**Дата вступления в силу: 1 ноября 2026 г.｜Версия: 1.3**

На этой странице описаны жизненный цикл данных сервиса Sonic (далее «сервис»), характер видов обработки, меры безопасности, известные ограничения и порядок реагирования на утечки данных. Страница разворачивает раздел 10 [Политики конфиденциальности](/ru/privacy-policy/); технические факты определяются фактической реализацией открытого кода и могут быть проверены аудитом исходного кода.

Уровень передачи — TLS по всей цепочке; уровень аутентификации построен на подписанных ключах HMAC-SHA256 и OAuth с PKCE; граничный уровень блокирует адреса внутренних сетей и метаданных; уровень хранения изолирован привязкой к петлевому адресу и зашифрованным туннелем. Справа — средства контроля, которыми вы распоряжаетесь сами.*

## 1. Жизненный цикл данных

| Этап | Описание |
| --- | --- |
| Сбор | Через вход Epomail OAuth получаются данные идентификации учётной записи (не сохраняются на диск); события поведения передаются плеером пакетами (можно отключить; не более 50 событий и 64 КБ в пакете); IP временно используется для анонимного ограничения частоты |
| Передача | HTTPS/TLS по всей цепочке; между плоскостью управления и плоскостью данных действует зашифрованный канал Cloudflare Tunnel с обязательной проверкой межсервисного ключа (X-Sonic-Engine-Key); заголовок клиентского адреса от границы к движку принимается только после проверки сервисного ключа на стороне движка |
| Хранение | SQLite в плоскости данных (режим WAL) в именованном томе `sonic-data` по пути `/app/data/sonic-recommend.sqlite`; при отказе открыть базу в производственной среде сервис недоступен (fail-closed), без тихой деградации |
| Использование | Статистические вычисления, связанные псевдонимизированными идентификаторами (рекомендации, популярность, похожесть); без ручной проверки содержимого, без модерации контента, без автоматизированных решений |
| Передача третьим лицам | См. [Перечень третьих лиц и международных передач](/ru/sub-processors/); без продажи и использования в рекламных целях |
| Удаление | События поведения автоматически уничтожаются через 90 дней (очистка запускается по каждой 1500-й записи и при запуске); очистка одним нажатием удаляет немедленно; записи ограничения частоты истекают через 120 секунд |

## 3. Меры защиты безопасности

### 3.1 Передача и доступ

1. **Шифрование по всей цепочке**: от браузера к границе и от границы к плоскости данных действует TLS; плоскость данных подключается через зашифрованный канал Cloudflare Tunnel, не публикуя портов напрямую в интернете; на стороне хоста проброшен только `127.0.0.1:8080`;
2. **Межсервисная проверка**: плоскость данных требует проверку X-Sonic-Engine-Key для всех маршрутов `/api`, `/proxy`, `/palette`; движок удаляет недоверенные входящие заголовки и восстанавливает заголовок клиентского адреса по адресу сокета, поэтому подделка всегда неэффективна;
3. **Деградация с явным уведомлением**: в режиме граничной деградации в заголовке ответа указывается `X-Sonic-Degraded: 1`, интерфейс синхронно показывает уведомление о деградации; без тихого переключения.

### 3.2 Аутентификация и ключи

1. **Поток OAuth**: параметры `state` и PKCE (S256) защищают от перехвата и повторного воспроизведения кода авторизации; транзакционные cookie действуют 600 секунд и только для пути `/api/auth`; при обратном вызове проверяются state, PKCE, код авторизации и защита от повтора; при отсутствии или аномалии любого звена следует безусловный отказ;
2. **Ключи API**: версионированный формат `sonic_live_v2`, подпись HMAC-SHA256, сравнение на сервере с постоянным временем выполнения через Web Crypto `crypto.subtle.verify`; строгая проверка версии, `kid`, `iat`/`exp` и `jti`; ключи без подписи и устаревшие ключи v1 отклоняются безусловно (fail-closed); срок действия при выпуске 30 дней, предел проверки 90 дней; ключи передаются только через заголовки запросов, канал `?api_key=` полностью удалён, чтобы ключи не утекали в журналы доступа, историю браузера или Referer;
3. **Механизм отзыва**: выход из системы немедленно отзывает текущую сессию; список отзыва `jti`, список отзыва субъектов и глобальная нижняя граница времени выпуска (`SONIC_REVOKED_JTIS`/`SONIC_REVOKED_SUBS`/`SONIC_TOKEN_MIN_IAT`) поддерживают массовое аннулирование; при привязке KV и включённом `SONIC_ENABLE_KEY_REVOCATION=1` поддерживается мгновенный отзыв; без настройки мгновенного отзыва соответствующие эндпоинты возвращают 501 с подсказкой использовать списки, не имитируя успешный отзыв;
4. **Атрибуты сессии**: `HttpOnly; Secure; SameSite=Lax`, срок действия не более 30 дней; перенаправление обратного вызова входа несёт только параметр состояния `?auth=success` и не возвращает ключей.

### 3.3 Защита исходящих запросов

1. **Перехват SSRF**: исходящие запросы к петлевым адресам, частным сетям RFC 1918, внутренним мостам Docker и адресам облачных метаданных (например, `169.254.169.254`) блокируются безусловно; выполняется проверка по двойному стеку IPv4 и IPv6; при каждом перенаправлении цель и результат разрешения DNS проверяются заново;
2. **Белый список доменов**: прокси аудио, обложек и пересылки допускает только HTTPS-цели и стандартные порты из контролируемого списка музыкальных CDN-доменов (`SONIC_ALLOWED_MUSIC_DOMAINS`);
3. **Очистка запросов**: вышестоящие запросы лишаются `Set-Cookie` и заголовков учётных данных и несут только фиксированный User-Agent, соответствующий Referer официального сайта и необходимый заголовок Range; исходящий IP обозначен замещающим адресом, настроенным оператором развертывания (по умолчанию документационный адрес RFC 5737), а не IP какого-либо пользователя.

### 3.4 Хранение и журналы

1. **Псевдонимизированное хранение**: события поведения связываются однонаправленными хеш-идентификаторами (усечённые значения SHA-256 с префиксами `usr_`/`anon_`); нет колонок с открытым адресом электронной почты и нет колонок IP; всего 6 таблиц хранения (канонические данные треков, отображения треков платформ, полнотекстовый индекс, события поведения, совместное прослушивание треков, агрегация поисковых запросов), при этом с личностью связана только таблица событий поведения;
2. **Хранение fail-closed**: отказ открыть базу данных в производственной среде означает отказ в обслуживании, а не тихую деградацию; резерв в памяти допускается только для разработки и тестов либо при явной настройке `SONIC_RECOMMEND_ALLOW_MEMORY_FALLBACK=1`;
3. **Минимизация журналов**: журнал доступа плоскости данных ведётся построчно в JSON и содержит только идентификатор запроса, метод, путь, код состояния и время обработки; строки запроса, IP, User-Agent, cookie, Authorization и тело запроса не записываются; необработанные исключения записывают только идентификатор запроса, имя ошибки и усечённое сообщение; журналы направляются в стандартный вывод Docker, политика ротации следует конфигурации Docker хоста; на стороне Cloudflare Pages отсутствуют собственные глобальные журналы доступа этого проекта;
4. **Резервное копирование**: резервное копирование базы данных выполняется консистентным снимком (VACUUM INTO) с проверкой целостности; файлы резервных копий содержат псевдонимизированные поведенческие данные и требуют защиты того же уровня, что и производственные данные;
5. **Изоляция контейнеров**: плоскость данных работает в стеке контейнеров Docker; вспомогательный контейнер ncm-api доступен только внутри сети compose (`ncm-api:3000`) и не публикуется в интернете; файл конфигурации `.env` требует прав 600.

### 3.5 Известные ограничения

Сервис является проектом с открытым кодом; оператор публикует следующие известные ограничения и продолжает работу над ними:

1. В формах развертывания без привязки нативного ограничителя Cloudflare ограничение частоты ведётся по KV или в памяти процесса и не является строго глобальным и точным;
2. Защита от DNS rebinding не устранена полностью; операторам развертывания следует дополнять её мерами на сетевом уровне;
3. Cookie `sonic_session` содержит подписанный ключ API; хищение cookie равнозначно хищению ключа, поэтому требуются безопасность устройства и своевременный выход из системы;
4. SQLite — архитектура с единым писателем, непригодная для форм развертывания с высокой конкуренцией записи;
5. Встроенный эндпоинт метрик Prometheus отсутствует; мониторинг опирается на журналы и внешнюю проверку доступности.

Полный перечень ограничений приведён в `docs/OPERATIONS.md` вышестоящего репозитория; операторы самостоятельного развертывания должны оценивать их применительно к своей форме развертывания.

## 4. Реагирование на утечки данных

1. **Внутренняя регистрация**: все утечки персональных данных регистрируются (статья 33, пункт 5 GDPR); оценка как низкого риска не освобождает от регистрации;
2. **Уведомление надзорного органа**: если утечка может создать риск для субъектов данных, уведомление компетентному надзорному органу по месту нахождения оператора направляется в течение 72 часов после того, как об утечке стало известно, с описанием характера утечки, категорий и объёма затронутых данных, возможных последствий и принятых мер (статья 33, пункты 1 и 3 GDPR);
3. **Уведомление субъектов данных**: если утечка может создать высокий риск, затронутые субъекты уведомляются без неоправданной задержки объявлением на платформе или иным действенным способом с описанием характера утечки и рекомендуемых мер (статья 34 GDPR); если риск эффективно устранён и высокий риск более не существует, уведомление можно не направлять, но обоснование решения должно быть записано;
4. **Меры реагирования**: немедленная изоляция затронутых систем, отзыв затронутых ключей и сессий (включая списки `jti` и глобальную нижнюю границу времени выпуска), оценка и устранение причин, запись всего хода обработки инцидента.

## 5. Защита данных по проектированию и по умолчанию

На этапе проектирования сервис реализует следующие меры (статья 25 GDPR):

1. **Псевдонимизация по умолчанию**: события поведения связываются хеш-идентификаторами с самого начала сбора; адреса электронной почты не сохраняются на диск; в базе данных нет колонок IP;
2. **Режим нулевого сбора**: при отключённой персонализации события не записываются в базу, а в публичном режиме сразу отбрасываются на сервере с честным указанием количества проигнорированных событий в подтверждении;
3. **Минимум клиентских данных**: рекомендательный контекст несёт лишь ограниченное количество избранных треков, недавних исполнителей и поисковых запросов, используется в памяти и не сохраняется; плеер не читает и не пишет `document.cookie`, ключи не попадают в localStorage;
4. **Высокорисковые цепочки, отключённые по умолчанию**: сторонние агрегированные вышестоящие сервисы (GDStudio, Lyriva) и цепочки обхода ограничений по умолчанию жёстко отключены и действуют только после явного включения оператором развертывания (переменной окружения присваивается 1);
5. **Очистка одним нажатием**: право на удаление реализовано напрямую функцией самостоятельного обслуживания, без ручных запросов; «Очистить все локальные данные» одновременно очищает серверный профиль, localStorage, sessionStorage и IndexedDB.

## 6. Обязанности операторов самостоятельного развертывания

С момента самостоятельного развертывания сервиса вы становитесь контролёром данных своих пользователей и обязаны:

1. **Информировать**: уведомлять пользователей о вопросах обработки данных (за основу можно взять [Политику конфиденциальности](/ru/privacy-policy/) этого сайта);
2. **Вести записи**: поддерживать записи видов обработки (статья 30 GDPR);
3. **Оценивать воздействие**: при возможном высоком риске проводить оценку влияния на защиту данных (статья 35 GDPR); объём оценки как минимум охватывает анонимные идентификаторы устройства, события поведения, временное использование IP для ограничения частоты, хеш-вычисление из электронной почты OAuth;
4. **Сверять конфигурацию**: убедиться, что следующие параметры согласуются с обязательствами вашей политики: срок хранения событий поведения (`SONIC_RECOMMEND_RETENTION_DAYS`, по умолчанию 90, минимум 7), путь записи на диск (`SONIC_RECOMMEND_DB_PATH`, значение `memory` отключает запись), переключатель резерва в памяти (`SONIC_RECOMMEND_ALLOW_MEMORY_FALLBACK`), переключатели сторонних цепочек (`SONIC_ENABLE_GDSTUDIO` и др.), параметры ограничения частоты (`SONIC_RATE_LIMIT_ANON_RPM`/`SONIC_RATE_LIMIT_AUTH_RPM`);
5. **Обеспечивать безопасность и поднадзорность**: настроить меры по разделу 3 (включая межсервисный ключ не короче 32 символов, права `.env` 600, закрытую от интернета плоскость данных) и по праву вашего местонахождения проходить проверки и надзор компетентных органов.

## 7. Проверяемость

Заявления сервиса о безопасности проверяемы по исходному коду: вся логика обработки, значения переключателей по умолчанию, структура хранения и форма журналов опубликованы в репозитории открытого кода; в вышестоящем репозитории есть также записи об устранении замечаний аудита безопасности (`docs/AUDIT_REMEDIATION.md`) и руководство по эксплуатации (`docs/OPERATIONS.md`). Технические факты документации сайта сверяются при обновлении версий; при обнаружении расхождения с исходным кодом приоритет имеет код, и документация немедленно исправляется.
