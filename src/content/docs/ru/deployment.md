**Дата вступления в силу: 1 ноября 2026 г.｜Версия: 1.4**

На этой странице описаны два сценария самостоятельного развертывания Sonic, основные переменные окружения, резервное копирование и восстановление, а также ключевые моменты эксплуатации. С момента развертывания развернувший становится контролёром данных своих пользователей; соответствующие обязанности приведены в разделе 6 документа [Обработка данных и меры безопасности](/ru/data-security/) и в документе [Правовые аспекты открытого кода и самостоятельного развертывания](/ru/open-source/); авторитетное изложение деталей операций — в `docs/OPERATIONS.md` вышестоящего репозитория.

## 1. Сценарий A: граничный шлюз Cloudflare Pages

```bash
git clone git@github.com:shijianus/sonic.git
cd sonic
corepack enable
corepack prepare pnpm@10.34.5 --activate
npm ci
pnpm --dir player install --frozen-lockfile
npm run build
npx wrangler pages deploy dist --project-name <你的项目名>
```

В панели управления Cloudflare Pages настройте зашифрованные переменные окружения: `SONIC_SECRET`, `SONIC_ENGINE_SECRET` (совпадающие со стороной VPS) и `SONIC_LOCAL_ENGINE_URL` (указывающий на домен туннеля вашей плоскости данных).

## 2. Сценарий B: локальный протокольный движок на Linux (Docker Compose)

```bash
mkdir -p /opt/sonic && cd /opt/sonic
git clone git@github.com:shijianus/sonic.git .
cp .env.example .env
chmod 600 .env    # 填入强随机 SONIC_ENGINE_SECRET 与 SONIC_SECRET
docker compose up -d --build
docker compose ps
curl -H "X-Sonic-Engine-Key: <YOUR_SECRET>" http://127.0.0.1:8080/api/sonic/engine/health
```

Состав стека: основной контейнер sonic-engine (на стороне хоста проброшен только `127.0.0.1:8080`), замкнутый во внутренней сети вспомогательный контейнер ncm-api, постоянное хранение SQLite (именованный том `sonic-data`). Плоскость данных подключается через Cloudflare Tunnel и не публикуется напрямую в интернете.

## 3. Основные переменные окружения

| Переменная | Описание |
| --- | --- |
| `SONIC_SECRET` | Ключ подписи ключей API, длина ≥ 32 символов (`openssl rand -base64 48`) |
| `SONIC_ENGINE_SECRET` | Межсервисный ключ, одинаковый на сторонах Pages и VPS |
| `SONIC_LOCAL_ENGINE_URL` | Адрес туннеля плоскости данных |
| `SONIC_ENABLE_NETEASE/QQ/KUGOU/KUWO` | Переключатели встроенных протоколов источников звука (по умолчанию 1) |
| `SONIC_ENABLE_AMLL/LRCLIB` | Переключатели дополнения текстов (по умолчанию 1) |
| `SONIC_ENABLE_GDSTUDIO/LYRIVA/UNBLOCK` | Сторонняя агрегация и обход ограничений (по умолчанию 0; должны оставаться отключёнными, кроме случаев действительной необходимости) |
| `SONIC_RECOMMEND_DB_PATH` | Путь записи поведенческих данных на диск; значение `memory` отключает запись |
| `SONIC_RECOMMEND_RETENTION_DAYS` | Срок хранения событий поведения в днях (по умолчанию 90, минимум 7) |
| `SONIC_RATE_LIMIT_ANON_RPM / AUTH_RPM` | Ограничение частоты запросов (по умолчанию 240/600) |
| `EPOMAIL_BASE_URL` и др. | Конфигурация Epomail OAuth |

Полный перечень приведён в `.env.example` вышестоящего репозитория; требования к согласованности уведомлений по переключателям, связанным с приватностью, изложены в разделе 6 документа [Обработка данных и меры безопасности](/ru/data-security/).

## 4. Резервное копирование и восстановление

1. **Резервное копирование**: скрипт консистентного снимка выполняет `VACUUM INTO` с проверкой целостности (`npm run backup:db`); файлы резервных копий содержат псевдонимизированные поведенческие данные и требуют защиты того же уровня, что и производственные данные;
2. **Восстановление**: после остановки сервиса снимок восстанавливается скриптом восстановления (`npm run restore:db`); в репозитории нет версионированной системы миграций, поэтому целевая версия восстановления должна совпадать с версией резервной копии;
3. **Ёмкость**: события поведения автоматически очищаются по сроку хранения 90 дней; объём базы данных растёт вместе с каноническими данными треков — следите за пространством тома.

## 5. Проверки работоспособности и откат

1. **Проверка работоспособности**: `GET /api/sonic/engine/health` (требуется сервисный ключ) возвращает состояние движка и предохранителя; граничный предохранитель при подряд идущих неудачах плоскости данных автоматически переходит в режим деградации;
2. **Журналы**: журнал доступа на стороне движка содержит только путь, метод, код состояния и время обработки (`docker compose logs`); строки запроса, IP, cookie и тело запроса не записываются;
3. **Откат**: на стороне Pages достаточно откатиться к предыдущей версии развертывания; на стороне плоскости данных выполняется `git checkout` предыдущего тега и заново `docker compose up -d --build`; перед откатом убедитесь в совместимости схемы SQLite (системы миграций нет).

## 6. Контрольный список развернувшего

Перед выводом в эксплуатацию проверьте по пунктам:

1. Оба ключа — сильные случайные и длиной ≥ 32 символов; права `.env` — 600;
2. Переключатели сторонних цепочек согласуются с вашим уведомлением о приватности (невключённые цепочки следует исключить из уведомления);
3. Срок хранения событий поведения и путь записи на диск соответствуют обязательствам вашей политики;
4. Плоскость данных доступна только через туннель, порты хоста не открыты в интернет;
5. План резервного копирования создан и проведена тренировка восстановления;
6. Вашим пользователям опубликован текст уведомления (за основу можно взять [Политику конфиденциальности](/ru/privacy-policy/) этого сайта).
